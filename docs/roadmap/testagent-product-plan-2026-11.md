## 产品判断

当前具备个人对话、设计流程、来源映射、人工及 Agent 补充、本地 Python 验证和基础协作，已经超出界面原型。但更接近“能跑通受控样例的验证工作台”，距离用户拿到陌生题目和 SDK 就能稳定找出问题，还缺少接入、分析预算、任务数据可靠性、缺陷复核四个关键闭环。

主路径应为：新建会话任务 → 导入题目和框架 → 接入检查 → 展示分析范围与预算 → 逐项补全需求/因子/场景 → 评审用例 → 生成及检查脚本 → 确认目标后执行 → 复核候选问题 → 修复复测。项目保存共享基线和目标环境，会话保存一次任务；运行记录保存某次执行快照，三者有明确关联。

| P1 | 执行已有 AST 检查、环境清理和进程树回收，但 `process.rs` 仍是本机 Python 进程 | 不将 `-I`、AST 检查或 Job Object 称为安全沙箱。增加可选容器/受限执行器、网络目标范围、资源配额和文件访问边界；之后分别实现 WSL/SSH，远端也要有取消、证据回传和失败清理。 |
| P2 / 企业发布门槛 | CSP 仍含 unsafe-eval；组织身份、令牌生命周期与多机部署验收不完整 | 静态编译 JSON 校验器、收紧 CSP；完善项目授权、令牌撤销/过期、TLS 部署、审计导出及恢复手册。基础角色控制已存在，不能描述为“完全没有权限”。 |
| P2 | `reviews/CaseReview.tsx` 仍有固定样例，引用搜索未发现生产入口 | 删除经引用检查确认的废弃组件及专属样式/文案；清理不等于删除真实历史产物。以实际使用路径持续复核样式与导航，避免新增重复的项目/任务选择器。 |

## 交互改进原则

- 左侧工作区/会话，中间对话和确认卡片，右侧可收纳的任务进度与产物入口。项目设置留在项目上下文，全局设置只管默认项。
- 新任务提供“题目 + 测试框架 + 目标环境”准备清单；缺框架可先完成设计，不能把未执行隐藏成成功。
- 场景树按子系统/功能/状态组织；表格用于筛选和批量评审，详情显示原文与映射。风险、未知预期、缺少因子组合优先显示。
- 覆盖灯保留已有层级：设计覆盖、人工声明、脚本映射、实际执行。新增断言证据到达及过期状态，不用一个绿色图标混淆这些含义。
- “新增场景/补充因子/重试失败批次/复测问题”从当前条目发起，自动带最小必要上下文；提交前显示改动范围。未保存编辑、网络重连和多成员冲突不得静默覆盖。
- 常见任务走预置流程。编排面向高级使用；工作流生成 Agent 最后加入，先只生成受支持节点的可校验草稿，不能自动授权执行。

## 实施顺序与里程碑

工作量为一名开发者的初步净开发人日，包含自动化测试及文档，不含等待内部环境、用户评审和 CI；完成第一阶段后重新估算。每阶段均须提供实测/模拟/未覆盖清单。

| 阶段 | 目标版本 | 工作量 | 交付及退出条件 |
| --- | --- | --- | --- |
| M0 收尾 | 0.8.5 | 当前批次 | CLI 扫描选择、文件/目录选择、高级手填；保存、取消、失败保留与刷新恢复通过；原生选择器目标环境验收单列；发布 release 包。 |
| M1 接入与预算 | 0.9.x | 5–8 人日 | 能力状态与连通检查、任务准备清单、分析预算预览、有界交叉调查、阶段化故障诊断。长题目不再隐式触发平方级调用；可定位到具体失败批次。 |
| M2 数据可靠性 | 0.10.x | 7–10 人日 | 个人 SQLite、文件化证据、迁移/备份/恢复、版本和任务事件。升级前后任务可继续；磁盘满和强制退出不损坏已提交数据。依赖 M1 的能力/预算数据契约。 |
| M3 可评审设计与框架 | 0.11.x | 10–15 人日 | 多源原文、场景树和约束因子、统一条目变更、用例编辑、SDK 接入与多文件 unittest。需求修订能列出失效范围；真实用户式 SDK 可形成设计到执行闭环。 |
| M4 找到可复现的问题 | 0.12.x | 10–15 人日 | 候选问题复核、状态探索、关系判定、稳定性复跑、缩减复现、修复复测。至少三个不同业务基准，正确参考目标与缺陷目标分开盲测，保存重复运行结果。 |
| M5 团队交付 | 0.13.x | 8–12 人日 | 个人到项目的提议合入、评论/通知、增量同步、权限与令牌生命周期；两台物理机器加一个 Agent 客户端完成冲突、离线重连和复核。依赖 M2/M3 稳定 ID 与修订协议。 |
| M6 企业发布门槛 | 1.0 候选 | 8–12 人日 | 执行隔离、目标执行器兼容矩阵、CSP/TLS/审计、安装升级回退、容量与恢复演练。WSL/SSH 只将实际验收通过的平台标为支持；未完成门槛继续 0.x。 |

发布补丁可以穿插，但不让补丁版本堆积未验收的大功能。先保留模块化单体、Rust 原生能力、Node 协作服务和明确端口接口，不引入微服务、消息队列或通用多 Agent 调度平台。

## 下一批具体任务

M1 首批实施（0.9.0）：已统一非 native 配置的运行能力提示和选择限制，建立[分批调用数量基线](../research/analysis-budget-baseline.md)，接入设计批次预算暂停/继续、进度、待调查关系、需求草稿阶段的分批预估及首次确认/继续时可选 1–64 批次的预算。首次额度进入批准历史。设置已提供主动短对话连通检查、时间记录、取消和配置失效；此检查不认证结构化流程兼容性。

0.9.9 补充调用前准备清单：复用实际运行的范围选择规则，展示保存版本、步骤、当前会话或节点绑定的实际 Agent、模型与配置来源，以及精确匹配当前配置的会话内短测结果。缺模型、失效绑定、非法框架或目标地址格式会在创建任务之前阻止发送并保留 Spec；缺框架可先做设计。未做短测、结构化能力和目标连通性保持待验证，不自动调用模型或探测目标。完整费用预算、主动目标连通检查、持久化检查历史及风险关系排序尚未交付。

## 衡量方式与验证纪律

关注首次成功设计耗时、实际有效调用数/输入量、任务恢复成功率、来源可定位率、未决覆盖缺口、稳定可复现缺陷数、参考目标误报和人工复核时间。没有真实计费数据时不估作零成本。

自动化回归、真实 CLI 调用、系统文件选择器、安装升级和两台物理机器协作分别记录。固定脚本复跑不能证明本次 Agent 发现能力；必须增加从未见过的 Spec/框架重新生成的盲测。代码和截图通过也不能代替目标环境的认证或实际操作验收。
