# 默认通用测试工作流

状态：首条需要重点打磨的产品流程。以测试需求 Spec 为入口，以可追溯的验证报告和后续动作计划为出口。角色可共享同一个本机 CLI，也可绑定不同 Profile。

当前实现：设计范围 7 节点 / 3 次确认；完整范围 13 节点 / 4 次确认，使用单文件 unittest 和本地执行。以下保留完整产品设计，包含尚未实现的逐条编辑、远程目标与缺陷提交；当前操作步骤及准确边界见[本地 Python 工作流](local-python-verification.md)。

## 输入约定

必选：需求文件、项目、测试目标和预期验证范围。可选：代码仓库 / 版本、历史用例、接口定义、用户模板、环境 Profile、测试数据、语言和预算。缺少信息先显示明确问题与阻塞项，不假定可访问生产环境。

默认内容语言沿用需求语言，界面语言由用户独立选择。导入原文必须留存不可变修订，后续每一步都引用来源版本。

## 阶段与交付物

| 阶段 / 角色 | 输入 | 输出 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 1. 导入与定位 | Spec 文件 | 文档修订、结构与锚点 | 可解析、编码及 hash 有效 |
| 2. 需求解析 Agent | 原文、验证范围 | 原子需求、验收点、歧义清单 | 结构有效、引用存在 |
| 3. 需求确认 | 需求与歧义 | 需求基线 / 仍阻塞项 | 用户确认版本与范围 |
| 4. 测试设计 Agent | 需求基线、领域策略 | 测试策略、场景树、覆盖义务和映射候选 | 每个场景可验证，映射能回原文 |
| 5. 覆盖评审 | 场景、映射、缺口 | 确认映射、灯态、排除理由 | 必需缺口已解决或显式阻塞 |
| 6. 用例设计 Agent | 已确认场景、预期 | 用例、数据、步骤、断言、适用条件 | 能对应到场景和验收点 |
| 7. 用例展示与确认 | 用例表与覆盖矩阵 | 人工编辑后的用例基线 | 用户完成评审，保留摘要 |
| 8. 用例开发 Agent | 用例基线、代码约定 / 模板 | 脚本、依赖、运行入口、用例→断言映射 | 静态检查通过，无法实现项明确 |
| 9. 环境预检 | 脚本清单、目标 Profile | 依赖与资源报告、最终执行计划 | 环境就绪、命令及证据契约有效 |
| 10. 执行确认 | 脚本 diff、目标与预算 | 绑定 hash 的执行授权 | 用户确认当前快照 |
| 11. 测试执行器 | 执行计划 | 逐用例报告、日志、证据 manifest | 执行终态已知、产物已校验 |
| 12. 判定分析 Agent + 规则 | 原始证据、断言、需求 | 规则结论、原因、未知项、覆盖状态 | 结论引用当前证据 |
| 13. 结果行为策略 | 判定与策略 | 报告、缺陷 / 补测 / 修复候选及动作记录 | 在授权与预算范围内执行 |

用例展示是独立评审阶段：支持按需求 / 场景查看、筛选缺失预期、批量确认及逐条修改。修改场景或需求会使确认失效；用户无需到聊天记录里找最终用例。

## 每条用例的最小内容

稳定 ID / revision、标题、关联需求和场景、优先级、前置条件、输入数据、步骤、预期结果、具体断言 / oracle、执行环境适用性、自动化方式及清理要求。不能以“结果正确”“页面正常”作为可执行预期。

开发 Agent 必须说明每条用例在哪个文件、函数和断言实现；手工用例标记 manual。测试数据如含敏感字段，只在安全存储保留，给 Agent 的上下文采用项目允许的脱敏视图。

## 可复用产物

原文快照、需求基线、测试策略、场景树、覆盖义务与映射、用例表、模板引用、脚本 diff、执行计划、逐用例证据和最终报告。默认导出 JSON + 可阅读 Markdown；团队报表格式在后续扩展，导出时保留稳定 ID 和版本。

## 缺口和失败分支

- 需求存在冲突：停在需求确认；问题及候选解释写入产物，不自行挑一个解释。
- 必需维度无场景：展示红灯，生成补充候选后重新评审；不先生成大量脚本掩盖缺口。
- 用户拒绝用例：只重做受影响用例，并检查开发产物是否失效。
- 模板参数缺失 / 框架不匹配：展示具体错误，可选 Agent 自实现；不静默改模板结构。
- 目标不可达：BLOCKED，保留已确认用例与脚本，环境恢复后从预检继续。
- 执行超时 / 远端失联：先对账，未知时不自动重复有副作用的测试。
- 业务断言失败：保留失败证据进入分析；重试通过也保留失败历史并可标记 flaky。
- 判定缺证据：INCONCLUSIVE，生成补证据计划，不能自动发布全通过报告。

测试 FAIL 作为执行产物中的业务结果传入分析，不直接令工作流引擎中断。执行器若能形成有效证据封套，即使包含 ERROR / INCONCLUSIVE 也进入判定；引擎自身故障无法形成封套时，由固定运行终结器保存失败摘要，避免仅因最后一个动作节点被阻塞而没有报告。

## 一次典型回放

输入登录锁定 Spec。需求解析指出“连续失败重置条件未定义”；用户澄清后冻结版本。场景生成遗漏 10 分钟边界时覆盖灯为红；补充并确认后转绿，此时执行灯仍为未运行。用例确认后按 pytest 模板开发，在 WSL 执行。第 5 次失败未锁定，规则判 FAIL；分析 Agent 引用断言和日志提出计数器问题，结果策略保存缺陷草稿及边界补测建议。

该旅程的成功标准是：即使判定为 FAIL，用户也能从结论一路回到运行证据、用例、场景和原始需求；产品不以“让测试变绿”作为优化目标。
