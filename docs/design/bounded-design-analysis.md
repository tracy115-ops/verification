# 有界分批需求与场景分析

## 目标与边界

需求或场景节点的单次 JSON 请求超过 24,000 UTF-8 字节时启用分批；小请求保持原路径。此改动降低单次输入和生成压力，不宣称已定位内部 CodeAgent 的初始化等待原因，也不改变 CLI 代理、模型或单次超时策略。

## 执行机制

需求按原文顺序切分，每段核心约 5,000 字节，优先在换行处分界，并保留边界上下文及原文 Markdown 标题路径。核心区间连续覆盖全部原文，Unicode 字符不截断。每批只发送该原文窗口，输出仍以完整 Spec 检查唯一引用，ID 按批次命名。合并只去除内容完全相同的条目，不猜测语义相同。

场景按已确认需求的序列化大小分组，发送组内需求和原文引用，生成因素及场景。引用只在需求字段中发送一次，sourceTextField 显式指向引用，不再重复发送 sourceSpec。随后检查各需求组的两两组合，专门寻找跨组权限、状态、资源和顺序约束；无跨组发现时可返回空增量。跨组输出必须关联两组需求，禁止把普通单组场景冒充跨组检查。最终因素和场景重新做完整关系校验。

两两检查不证明所有三组及以上高阶组合已完整覆盖，人工覆盖评审仍不可跳过。总产物沿用现有 Schema 上限；过大的单条输入或最终产物明确失败，不静默截短。

当前需求组最多 32 组（最多 528 次本地组与两两检查），单条需求序列化最多 8,000 字节，单节点恢复检查点最多 256,000 字节。24,000 字节是首版请求预算，不是模型的 token 上限。超出预算时明确失败并保留先前结果，避免无界组合与存储增长；这些是任务规模预算，不限制人工重试次数。

## 恢复与证据

每批保存版本、包含 Spec / Profile / 节点 / 澄清 / 排除项的签名、批次索引、已验证结果及结果 SHA-256。重试重新生成计划并验证缓存，跳过完成批次；取消后同样可以继续。每次模型调用使用独立 turn ID，仍绑定原会话和节点。总流程 deadline 继续生效，人工重试续用原有恢复规则。额外短调用会带来请求开销，不保证总耗时必然减少。

引用失败时保留该批待修复内容及已完成批次。人工修复仅完成该批，节点恢复 pending；剩余批次及组间检查完成之前不进入需求评审。缓存结构不可信：导入、恢复及运行时分别检查结构、索引、签名和语义引用。

右侧在现有节点内显示已保存批次 / 总批次和组间检查进度。批次完成不表示整个节点完成；仅最终合并校验成功后进入既有人审。
