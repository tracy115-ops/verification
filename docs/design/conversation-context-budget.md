# 会话上下文预算

## 输入范围

普通对话通过新 CLI 进程执行，原先每次携带最近 20 条完整消息。消息条数不能控制体积：旧 Spec 和长回复可能让“你好”也带上大量上下文。

默认 recent 模式保留最近最多 20 条，按 JSON UTF-8 体积控制在约 32 KiB；最新消息保持完整，超过预算时优先保留当前输入，最终仍受 128 KiB 请求上限约束。缩减后去掉失去原用户输入的开头助手消息，避免只保留旧答案造成上下文误导。省略数量在输入区展示，聊天记录和任务产物不删除。

current 仅发送当前消息；full 发送全部状态为 complete 的消息，过大时仍拒绝并提示输入限制。当前上下文选择属于输入区状态，切换会话后恢复默认 recent。本轮不是 Agent 自动语义总结，也不承诺裁减后保留所有旧事实；需要完整原文时应选择 full 或在当前消息中明确提供必要内容。

## 流程任务

流程节点使用 Spec 与显式输入，不复用普通聊天的历史窗口。需求解析中，当文档输入与 sourceSpec 完全相同时，只在 sourceSpec 发送完整原文，文档输入保留元数据和 sourceTextField 引用。原始 DocumentRevision、Spec、评审与产物不变。

## 诊断

cli.started 记录实际 promptBytes。cli.progress 每 15 秒记录原始输出字节、协议事件和公开正文长度；原始字节在收到完整行前即可统计。未知事件名用固定 unknown，不记录原始数据或模型思考。

新会话回复快、旧会话慢支持优先检查上下文，但不能单凭这个对照确认流程超时根因。相同工作流的短 Spec 对照、实际请求体积和直接 CLI 对照仍有价值。
