# 受监督的桌面更新交接

## 问题与机制

直接启动安装器然后退出无法确认安装是否完成，也无法在重启失败时留下过程结果。更新器改为使用当前已安装二进制的副本，以专用参数进入原生工作模式，在初始化桌面 WebView 前处理更新请求。

下载包通过原有大小和 SHA-256 检查后，工作台将更新进程和有界 JSON 请求写入更新缓存。Windows Shell 启动更新进程，工作台退出。更新进程按 PID 等待旧进程结束，最长 60 秒；不强杀仍运行的旧应用。随后再次校验包，以 /UPDATE /S 安装，完整目录参数最后传入；等待退出最长 600 秒。非零退出、启动失败和重启失败分别记录。安装成功后启动目标应用。

阶段记录不含需求、凭据和安装路径，仅包含版本、状态和退出码。下次启动的程序比较自身版本和目标版本，将结果写入两文件滚动诊断日志。restart_started 只表示启动请求发出，completed 需要程序启动后核对版本。

## 验证边界

安装前的异步校验使用堆分配缓冲区，避免跨 await 的大数组随 IPC future 在 Windows WebView 回调栈上构造。回归约束同时检查校验 future 与完整安装 future 小于 16 KiB；不能仅靠加大线程栈规避。

本地单元测试检查任务大小、安装包篡改拒绝和状态记录。GitHub 临时机器使用包含空格的安装目录，先通过实际 release WebView 的原生 IPC 调用安装命令，确认缺少下载包时正常返回错误且应用继续响应；随后复制 release 二进制作为更新进程，等待仍运行的应用退出后再安装，并确认重启进程持续存活。测试只在启动的测试进程上启用回环调试端口，不改变正式应用配置。

IPC 拒绝测试和安装器测试仍不能替代完整的界面升级验收。人工验收需记录当前版本、检查与下载、确认安装、目标版本启动以及原有会话保留；阶段记录中的 completed 才能作为重启后版本确认。

受管环境的应用白名单、端点防护、目录权限仍可能阻止进程启动；此时需要目标机器阶段记录和退出码。旧版本的交接逻辑无法通过下载新包提前改变，首次迁移可能需要手动安装。安装失败不承诺自动回滚二进制；业务数据恢复与跨版本数据迁移需要独立验收。
