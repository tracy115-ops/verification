# 深层黑盒问题发现计划

## 目标与判定

面向只有题目、外部接口与测试框架的项目，发现跨调用、跨身份和跨资源的行为违约。深度不以用例数量或模型声称的缺陷数衡量：必须保留原文规则、可观测判定、实际请求响应和可复现方法；正确参考目标不得误报。

## 分期交付

| 阶段 | 能力 | 验收方式 |
| --- | --- | --- |
| D1 当前实现 | 生产设计/分批/用例/脚本共用有界调查指引；状态序列、幂等作用域、守恒关系、依赖失败、并发历史 | 真实 CLI 只看题目与框架生成 Python；独立缺陷变体逐个执行，正确参考零失败 |
| D2 计划 | 类型化探索模型：状态、动作、前置条件、观察点、关系约束、需求 ID；范围与预算评审 | 对 Agent 模型做结构、引用与可观测性校验；未声明规则不成为断言 |
| D3 计划 | 有界状态序列/因子组合生成，执行历史重放，保留随机种子，缩减复现序列 | 缩减时重置并重放，保留相同违约判定；失败动作的前置条件变化不能冒充成功缩减 |
| D4 计划 | 并发调度历史、可控外部故障、补偿与重连；多 Agent/人工补充高风险旅程 | 仅在用户授权环境执行；提交增量建议，复审后进入执行计划，不共享个人 CLI 凭据 |
| D5 计划 | 候选缺陷复核、稳定性复跑、按证据聚合、最小复现包 | 区分稳定失败、间歇失败、执行错误与未知预期；不凭失败用例名称认定同根因 |

## 当前接入方式

保持既有产物和三个设计评审关口。`deepTestingGuidance` 作为版本化任务输入传给场景、用例和脚本节点；分批任务保留该输入。场景用已有 dimension / expected / requirementIds 表达方法、关系和引用，用例明确多步操作及观察点。脚本在单个独立方法内完成一个旅程，通过框架变量捕获运行时资源，不使用固定伪造 ID。

本阶段没有上线自动状态空间搜索、随机模糊执行或最小化器；示例基准也不等于用户项目的完整发现率。缺少时钟、故障注入、状态查询或身份能力时，记录实际受阻的判定，而不假定所有系统都必须具有这些能力。

## 基准原则

每个变体只植入一个故障；普通正常路径应通过。生成脚本不接收目标源码或缺陷清单；执行后再核对变体敏感性。完整参考目标、原脚本重跑和逐变体结果一起保存。模型问题、断言失败与框架错误分开，范围排除保留审计，不计为覆盖。
