# 产品定位与头脑风暴

状态：产品提案。首版假设用户在 Windows 本机处理代码和需求，可能把测试交给 Linux SSH 主机或 WSL；桌面形态是推荐，并非用户已确认的平台限制。

## 产品要解决什么

建立一个“有需求依据、有覆盖解释、有运行证据、有后续动作”的验证工作台。让用户复用已安装、已登录的 Agent CLI，并把一轮验证沉淀为下次能复用的工作流。

核心对象是验证项目和版本化产物：对话用于澄清，产物用于评审，工作流用于复现。多个专业 Agent 是角色，首版可由同一个 CLI 顺序承担；不要求同时常驻多个进程。

## 一条完整的用户旅程

1. 创建项目，选代码仓库、需求文档与默认语言。
2. 检测本机 CLI，复用登录或新建 Provider Profile，通过能力与连接检查。
3. 选“通用测试”，或描述“先做接口冒烟，再按日志归因”等目标，由 Agent 生成工作流草稿并保存。
4. 导入 Spec。先确认需求拆解和歧义，再生成测试策略与场景树。
5. 在原文旁查看需求与场景双向映射；发现无映射需求、无依据场景、缺少边界与异常分支。
6. 查看、编辑、确认用例；选择 Agent 自写脚本或按已有模板生成。
7. 预检依赖和环境，确认本轮执行计划，在本地、SSH 或 WSL 执行。
8. 查看逐用例证据、失败归因与不确定项，系统给出整体结果和覆盖缺口。
9. 根据规则归档、补测、生成缺陷草稿、有限重试，或生成修复提案并等待授权。

## 关键概念必须分开

| 概念 | 例子 | 决定什么 |
| --- | --- | --- |
| Agent 角色 | 测试设计、用例开发、判定分析 | 做哪项工作、输入输出和允许工具 |
| CLI Driver | Claude Code、Codex、Pi | 如何启动本机 Agent 并读取事件 |
| Provider Profile | 企业网关、已有订阅、兼容 API | 模型、协议、鉴权、预算 |
| Execution Target | 本地 Windows、SSH Linux、WSL Ubuntu | 测试脚本在哪个 OS 和工作目录执行 |
| Workflow | 通用测试、接口回归、自定义流程 | 节点依赖、评审、失败策略与复用 |

切换模型不自动切换执行机器；同一角色可绑定不同 CLI，同一工作流可选择不同目标环境。

## 产品交互建议

建议主工作区以“需求原文 / 场景与用例 / 证据与结论”关联查看，评审聚焦产物差异。运行面板展示阶段、当前输入版本、耗时和阻塞原因。工作流初期用步骤列表与表单编辑即可；图形画布后置。

需求和场景应分别显示设计覆盖、用例就绪、执行结果，不以单一总分掩盖风险。状态同时配文字、图标和原因，不能仅靠红绿颜色区分。点亮只表示满足已定义的检查维度，不证明所有可能场景都已发现。

## 值得打磨的能力

| 优先级 | 想法 | 价值与约束 |
| --- | --- | --- |
| P0 | 双向点选原文与场景 | 让用户能快速检查生成内容有无依据 |
| P0 | 覆盖缺口清单 | 先补遗漏，再大量生成用例 |
| P0 | 可编辑用例与阶段确认 | 避免脚本在需求未明确时自动落地 |
| P0 | 证据支持的判定 | 缺报告、缺断言或环境故障不算通过 |
| P1 | 自定义工作流生成并保存 | 可复用接口回归、冒烟及特殊验证流程 |
| P1 | 模板契约与局部重生成 | 保留团队脚本规范及用户手工修改 |
| P1 | 需求变化影响分析 | 原文变化后定位哪些映射、用例和脚本需复核 |
| P2 | 第二个 Agent 做覆盖审查 | 减少同一生成器盲点；模型共识不能替代证据 |
| P2 | 历史失败画像、风险驱动选测 | 积累真实运行后再做，不先造推荐模型 |
| P2 | 团队模板库、集中 Runner、CI 接入 | 本地闭环稳定后，建设权限与协作 |

## 首版范围建议

先用 Markdown / 纯文本 Spec，构建一个 CLI 的端到端验证闭环，再按兼容契约接第二个 CLI。默认模板可选择 pytest 作为首个验证样例；测试框架是可替换能力，不强制业务项目使用 Python。

产品最终需覆盖 Claude / Codex / Pi、Provider 快速配置、自定义工作流、模板开发和三种执行目标。它们应按阶段验收，不把最小闭环误称为全部完成。PDF / DOCX 精确定位、OCR、集中权限与云服务不放入最早阶段。

## 待产品评审的问题

- 桌面优先是否适合目标团队？若首发必须浏览器协作，沿用领域核心，改由本地 Runner 连接中心服务。
- 首个测试领域是 API、Web UI、嵌入式、EDA 还是通用脚本？它决定默认模板、原始证据和判定器。
- 用户脚本模板是否已有结果格式、依赖和运行命令？没有时需先约定模板 manifest。
- “结果后的 Agent 行为”首期做到缺陷草稿 / 补测，还是进入产品代码修复？建议先草稿、再独立 worktree 修复提案。
- 企业文档允许发往哪些 Provider、是否允许云模型？部署配置应可按项目限制；本地优先不代表模型推理必然离线。

以上问题记录为后续决策，不阻止本轮方案与验证计划归档。
