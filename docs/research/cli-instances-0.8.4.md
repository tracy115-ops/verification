# CLI 多实例隔离与验证

## 问题与修复

此前所有同类原生 Agent 都通过同一套 PATH 选择 CLI。设置中的模型 ID 无法指定安装实例，也无法指定该实例的 Claude 配置目录。因此本机一个实例调用成功，不能证明另一台设备或另一套配置可用。

`AgentProfile.launch` 保存可选绝对路径 `executablePath` 和 Claude 专属 `configDirectory`。同一组字段进入所有 `TurnRequest`；运行快照保留绑定，重试不会静默切换实例。显式脚本保留其环境设置，不执行 npm shim 优化。错误路径不回退。

设置入口：设置 → Agent 与 Provider → 对应 Agent 的 CLI 实例。可建立多个不同名称的原生配置并分别绑定。配置目录指向已配置的目录；不应填写密钥，也不自动复制其他目录的凭据。原生 CLI 仍继承应用进程环境，因此已有环境变量也可能影响认证与服务地址。

## 实际验证与边界

- Windows 原生进程测试创建两个带空格路径的 `.cmd` 包装实例，分别输出实例标识及配置目录，确认包装环境保留、调用之间不串目录。
- 显式无效路径在存在系统 CLI 的情况下仍返回 `cli_path_invalid`。
- 前端契约验证绑定保存、刷新恢复、聊天传输、流程三个设计节点及快照隔离；导出不携带本机路径。
- 通过更新后的 Rust `turn` 控制台入口，显式绑定本机 `claude.cmd` 与已有配置目录，请求模型 `glm-5.3-flash`，返回 `QA_OK`，状态 `completed`。这是本机继承环境中的自定义网关验证，不能证明真实 GLM 服务、用户机器或所有 Claude 配置可用。
- 生产界面测试使用离线 IPC 核对真实按钮操作与发送参数，不将模拟回复当作原生推理验收。

本轮结果：`npm run check` 的 197 项单测通过；58 项生产界面测试、9 项开发界面测试、4 项协作测试通过；`cargo test --workspace --locked` 通过（3 项需要显式环境的测试保持忽略）；2 项真实本地 Python 工作流通过。深层黑盒脚本复用回归识别 6 个缺陷变体，参考实现无失败。本轮没有重新通过原生桌面 GUI 启动或安装升级验收；先前启动动作被自动审批策略拒绝，不将浏览器测试记作该项通过。

Claude 用户与项目配置作用域见[官方设置说明](https://code.claude.com/docs/en/settings)。GLM 的 Claude 配置需要服务地址和认证，见[官方接入说明](https://docs.z.ai/devpack/tool/claude)；用户可能使用其他内部网关，应以所选实例的实际配置为准。
