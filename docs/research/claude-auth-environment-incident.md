# Claude 桌面认证环境差异

2026-11-05，针对 0.9.2 用户桌面连续 `cli_auth_failed` 的实际排查。

## 证据

桌面日志记录约一秒内收到终态认证失败，而非超时。用户级和系统级注册表没有常见 Anthropic 认证/地址变量；默认 Claude 用户 settings 未发现认证字段，常见 OAuth 凭据文件不存在。当前编码终端则存在临时 API 认证和自定义服务地址变量（只检查存在性，未输出值）。

对同一个本机 `claude.cmd`、模型请求 `glm-5.3-flash`、默认配置目录和固定短请求做原生进程对照：清除子进程的临时 Anthropic/OAuth 变量时返回 `cli_auth_failed`；保留当前终端环境时正常终止并返回预期标记。前者模拟关键桌面环境差异，不能声称完整复制了任意进程环境。

因此此前编码终端短调用成功不能认证用户桌面可用。尤其自定义网关中的模型名称请求成功，也不能证明真实第三方模型服务及其授权已配置完成。

## 修正与恢复边界

认证失败时增加只读来源检查：桌面进程的认证变量是否存在、当前配置目录、settings 认证字段/密钥助手是否存在、常见登录文件是否存在、是否有自定义服务地址。只返回布尔值和目录，不返回凭据、URL 或配置全文，不执行密钥助手。发现来源不代表凭据有效；未发现常见来源也不排除其他组织机制。

GLM 等第三方模型必须在用户指定的 Claude 原生配置中具备有效服务地址和认证；已有工作配置可通过实例目录复用。官方账户则使用原生登录。若只在某个用户终端配置了临时变量，可由用户从该已验证的终端启动应用以继承环境，但不会自动把编码环境的临时凭据复制到桌面或磁盘。

机器上缺少有效认证时，应用不能自动补出凭据。恢复需要用户在本机完成原生认证，或提供已有工作启动器/配置目录的位置；不得要求在聊天里发送 API Key。

本轮原生 UI 自动化宿主两次报告 `native pipe is unavailable`，无法操作现有桌面窗口；没有尝试绕过宿主或把浏览器回归当作桌面操作完成。

## 后续定位：独立设置文件

继续只检查常见本机配置的字段存在性后，发现非默认设置备份包含 Provider 配置。没有覆盖默认设置或复制凭据。清除测试子进程的临时 Anthropic/OAuth 环境变量，显式传入该文件的 `--settings` 并请求 `glm-5.3-flash`，真实已安装 Claude 正常完成固定标记短调用；随后通过应用相同 Rust `run_turn` 驱动再次完成。由此确认“默认配置缺少认证”不能推导成“用户没有可用认证”；可用配置在独立文件中，应用此前遗漏了该接入方式。该文件尚未被用户确认就是日常终端使用的文件。

修复贯通配置保存、文件选择、模型字段读取、来源诊断与 CLI 参数传递。运行时保持参数分离；带空格路径的 Windows 启动器回归同时验证配置目录与独立文件。独立文件与目录绑定均不包含凭据本身。
