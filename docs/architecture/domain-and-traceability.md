# 领域模型、需求映射与点灯

状态：核心产品设计。点灯的含义必须可以解释、复算和回到原文核对。

## 追溯主链

```mermaid
flowchart LR
  DOC[文档修订 / 原文锚点] --> REQ[原子需求及验收点]
  REQ --> LINK[已评审覆盖关系]
  SCN[场景树的可验证叶子] --> LINK
  SCN --> CASE[测试用例修订]
  CASE --> SCRIPT[脚本 / 断言 / 模板修订]
  SCRIPT --> ATT[目标环境中的执行 attempt]
  ATT --> EVID[证据 / 检查结果]
  EVID --> VER[判定与后续动作]
```

需求与场景是多对多；场景树用于组织，覆盖以可验证叶子为主，不因父节点有一条映射就认定所有子节点覆盖。允许一条用例验证多个场景，但每条关联都应指明具体断言。

## 关键实体

| 实体 | 核心字段 / 规则 |
| --- | --- |
| `DocumentRevision` | 文档 ID、修订、媒体类型、源文件 hash、内容语言、导入器版本 |
| `SourceAnchor` | 修订 ID、段落 / 行范围、规范化字符区间、原文摘录及摘录 hash |
| `RequirementRevision` | 稳定需求 ID、文本、来源锚点、优先级、验收点、歧义和状态 |
| `CoverageObligation` | 需求修订、验证维度、适用性、理由；由规则建议、用户确认 |
| `ScenarioRevision` | 稳定场景 ID、父节点、意图、前置条件、变量 / 分支及预期 |
| `CoverageLinkRevision` | 需求 / 验收点修订、场景修订、维度、来源、建议理由、确认状态 |
| `TestCaseRevision` | 步骤、数据、预期、断言、场景关联、执行适用条件 |
| `ImplementationRevision` | 脚本 hash、用例修订、模板修订、断言映射、依赖清单 |
| `ExecutionAttempt` | 代码与输入快照、目标、开始 / 完成时间、状态、日志与证据引用 |
| `Verdict` / `ActionDecision` | 范围、规则版本、证据引用、不确定项、建议和执行记录 |

实体用稳定 ID 表示身份，用 revision 表示不可变内容；删除以归档 / 墓碑保留历史引用。用户可见中文名称不作为关联键。

## 原文锚点如何可靠定位

首版支持 UTF-8 Markdown / 文本，导入时保存原文件及统一换行的规范化文本，锚点明确基于哪份文本。字符偏移统一采用 Unicode code point，不直接混用 JavaScript UTF-16 偏移；前端需要转换或由后端返回显示区间。

锚点组合使用文档修订、段落 ID、区间、引文和 hash。原文更新生成新 revision，尝试通过差异和引文匹配迁移锚点；重复引文、多义匹配或找不到原文时标记待复核。不得把旧页码 / 行号直接套到新版本。

后续 PDF / DOCX 需要媒体专属定位（页码、块 / 段落 ID、版面坐标和解析版本）；扫描件还需 OCR 置信信息。首版没有这些能力时应明确拒绝或保留附件，不伪造精确跳转。

## 覆盖关系的建立与评审

Agent 建议映射并给出原文引用、验收点、验证维度和解释；系统校验锚点及 ID 是否真实存在。用户可双向点击、手工新增 / 拒绝映射，并查看“需求无场景”和“场景无需求”列表。

生成器的 confidence 只是建议排序，不用于点亮。映射经确认后才纳入正式覆盖；补充的安全 / 健壮性场景可标记为风险派生，保留推导理由，不必伪造 Spec 来源。

## 三类独立状态

| 维度 | 状态示例 | 判断依据 |
| --- | --- | --- |
| 设计覆盖灯 | 灰 / 红 / 黄 / 绿 / 蓝 | 需求适用性、验证维度及映射确认 |
| 用例就绪灯 | 待生成 / 待评审 / 已确认 / 已实现 / 失效 | 对应版本用例、脚本及断言关联 |
| 执行结果灯 | 未运行 / 运行中 / PASS / FAIL / ERROR / INCONCLUSIVE / BLOCKED | 当前运行快照的证据与确定性规则 |

设计覆盖灯建议：

- 灰：需求未完成拆解或适用维度待确认，尚不能评价。
- 红：已确认范围内存在完全没有有效场景映射的必需验证项。
- 黄：有候选映射，但尚未评审、仅部分覆盖、存在歧义或版本失效。
- 绿：所有适用必需验证项都有当前版本、已确认且无悬空引用的场景映射。
- 蓝：明确不适用 / 延后，必须显示理由与确认者；不混入绿灯。

每个灯提供文字、图标、计算依据和版本。场景树聚合优先显示未覆盖 / 待确认项，再显示全绿或全不适用；没有子节点不能按空集合直接判绿。实际交互排序可再评审，但计算规则必须固定版本。

## 完整性检查不是“有连线就算覆盖”

为每条需求建立适用的 `CoverageObligation`，例如正常、边界、错误、权限、状态转换、并发 / 性能和国际化。按领域和风险选择，不把所有维度强套到每条需求；排除项需说明理由。

至少检查：缺失维度、没有预期结果的场景、不可观察的断言、只有成功路径、没有来源的业务场景、多个冲突需求、重复场景和不可达分支。Agent 做发现建议，系统执行明确的结构检查，用户确认业务完整性。

结构覆盖率 = 有有效确认映射的适用必需验证项 / 所有适用必需验证项。分母为零时显示 N/A。需求数、覆盖义务数、未评审数和排除数一起展示；风险加权分数只作辅助，不能掩盖高优先级红灯。没有任何算法可仅凭关联图证明自然语言需求的语义完全覆盖。

## 示例：登录失败锁定

Spec `REQ-LOGIN-007@r1`：“同一账号在 10 分钟内连续失败 5 次后锁定 15 分钟。”

| 验证项 | 场景 | 首次映射状态 |
| --- | --- | --- |
| 正常 | 第 1–4 次失败不锁定 | 已确认 |
| 阈值 | 第 5 次失败触发锁定 | 已确认 |
| 时间窗口 | 第 5 次在 10 分钟边界 / 窗口外 | 缺失，红灯 |
| 解除 | 15 分钟边界、锁定中正确密码 | 候选，黄灯 |
| 作用域 | 另一个账号是否独立 | 待澄清 |

还需澄清“连续失败”是否被成功登录重置、窗口是滚动还是固定，以及并发失败如何计数。澄清前不能因已有五条场景就全绿。

## 变更传播

如果阈值由 5 改为 3，系统保存 `REQ-LOGIN-007@r2`，将关联映射、用例、断言和脚本标记 stale，展示受影响子图。用户确认哪些仍适用，再生成差异和新运行；过去的 PASS 保留在 r1 历史，不能展示为 r2 已验证。

本轮运行以被冻结的需求、场景、用例和脚本修订为基准；中途改动另开 revision / run，保证可复现与结果可解释。
